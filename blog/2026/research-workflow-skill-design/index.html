研究工作流與 Claude Code Skill 設計：討論記錄

Created on June 12, 2026

2026   ·   AI協作   研究工作流   Claude Code   學術方法   ·   notes

一、起點：該不該設立工作流節點？

討論始於一個實務疑惑：Claude Code 能自動完成資料清理，那麼是直接丟資料要結果，還是建立有節點的工作流程？

結論是後者，理由不僅是品質控管，更是學術研究的本質要求。資料清理不是中性的技術步驟，而是一連串影響結果的研究決策（遺漏值處理、極端值判定等），這些決策必須能寫進方法章節、回應審稿質疑。「AI 清的，我不確定它做了什麼」在學術上不可接受。實務上設四個節點即可：清理前的描述性報告、刪除/插補/轉換前的方案確認、清理後的日誌產出、保留可重跑腳本。Claude Code 仍做所有苦工，研究者只在決策點保留否決權。

二、如何免於重複敘述：三層機制

這套工作流不需每次重講，Claude Code 提供分層的固化機制：

  1. CLAUDE.md（記憶）：專案層級放該專案的特殊規範，個人層級（~/.claude/CLAUDE.md）放跨專案通用原則。每次 session 自動讀取。
  2. 自訂指令/Skill：把完整流程封裝成可呼叫的指令，一行啟動整套程序。
  3. Hooks（硬性防呆）：對絕不能出錯的事項（如保護原始資料）設置強制攔截，不依賴模型自覺。

建議路徑：先寫專案 CLAUDE.md，流程穩定後封裝成指令，關鍵事項加 hooks。

三、架構抉擇：清理該獨立成專案還是內嵌各專案？

關鍵在區分「方法論可複用，執行與產物屬於專案」。清理決策依附於研究設計（同一資料做不同分析，處理方式不同），且可重現性要求清理腳本、日誌與分析程式碼同住一個專案，否則資料來源鏈會斷裂。因此預設做法是清理內嵌於各研究專案，方法論抽到個人層級的 skill 複用。

唯一例外：同一資料來源餵養多個研究專案時（長期調查資料庫、實驗室核心資料），應建立獨立的資料管線專案，產出有版本號的標準化清理資料集，各專案引用特定版本再做二次處理，避免不同論文出現不一致的清理版本。

判斷準則一句話：「這份資料會不會被第二個專案用到？」

四、核心領悟：Skill 的真實用途

過去覺得 skill 多此一舉，因為 Claude Code 臨場發揮就能完成任務。這次體悟到：skill 的價值在「重複」的維度上才顯現——它解決的不是「會不會做」，而是「每次做的方式一不一致」。寫成 skill，方法論就被固定下來，三個月後或學生接手，流程依然一致。Skill 是把個人研究 SOP 程式化，累積的是可帶著走、持續精煉的工作資產。

五、典範轉移：從「開發工具」到「沉澱方法論」

最大的思維翻轉：過去想開發一體適用的工具來自動化各階段性工作（資料處理、文獻整理），再拼湊結果。但研究工作是「相似而不相同的重複」，每份資料、每份研究都有特殊性，工具必須把所有變化預先寫死，結果不是工具臃腫就是削足適履。

新模式剛好相反：skill 固定方法論與品質標準（檢查什麼、哪裡該停、產出格式），把面對特殊性的彈性留給模型臨場判斷。以前是把判斷力寫進工具，現在是把判斷的「原則」寫進 skill。固定該固定的，彈性該彈性的——這是 AI 時代自動化與傳統自動化的本質差別。

對研究者而言，skill 庫會隨研究生涯成長：每完成一個專案，沉澱的不是又一個待維護的工具，而是更精煉的方法論。它記錄的是你如何思考研究，因此不會隨技術實作過時。

行動清單

  • 在個人層級 ~/.claude/CLAUDE.md 寫入通用原則（決策需確認、產出日誌、可重跑腳本）
  • 建立 ~/.claude/skills/data-cleaning，固化標準清理流程模板
  • 各專案 CLAUDE.md 只寫專案特有規範
  • 對長期共用的資料來源，評估建立版本化資料管線專案
  • 每次發現流程不順，直接修改 SKILL.md，讓改進沉澱
