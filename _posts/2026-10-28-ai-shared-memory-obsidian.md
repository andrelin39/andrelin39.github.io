在 Claude Code、Codex 這類 AI agent 出現之前，要讓 AI 幫忙跑程式，流程通常是這樣的：在對話視窗下 prompt，請 AI 寫一段程式碼，再複製貼到 IDE（例如 VS Code、RStudio、Colab）去執行。這樣確實省下大量寫程式的時間，但麻煩也不少。程式碼要反覆複製貼上，出錯了還得把錯誤訊息貼回去給 AI 修改。AI 看不到你的檔案和執行環境，只能「盲寫」，所以常常一跑就出錯。更不用說專案管理和版本控制，幾乎無從做起。

AI agent 出現後，這些問題大幅改善了。agent 可以直接讀寫專案資料夾裡的檔案、自己執行程式，看到錯誤後也能自己修正。於是很多人習慣把所有事情都交給 agent：在 agent 裡對話、規劃、執行，最後再請它驗證結果。

## 球員兼裁判的問題

但這裡有個地方怪怪的。讓同一個 AI 自己規劃、自己執行、最後還自己驗證，就像球員兼裁判。它很容易沿著原本的思路「確認」自己是對的，反而看不到自己的盲點。

所以我的做法是把角色拆開：

- **Chat（對話型 AI）**：跟我討論、規劃專案的整體架構與方向，並負責驗證最後的執行結果。它主要產出的是文字形式的 prompt（任務說明），幾乎不直接撰寫要執行的程式碼。
- **AI agent**：負責執行層面，依照 Chat 提供的 prompt 撰寫必要的程式碼並實際執行。

這樣一來，「規劃與驗證」和「執行」就由不同的角色負責。想更嚴謹的話，還可以跨 AI 分工，例如用 Claude 規劃、Codex 執行（或反過來），讓不同模型互相檢查。

## 什麼是「AI 失智」

但這又衍生出新的問題：我還是得把 Chat 的 prompt 貼給 agent，再把 agent 的結果貼回給 Chat，一樣很麻煩！而且每開一個新對話，AI 就忘了前面做過什麼。這就是我說的 **「AI 失智」**。

## 用 Obsidian 建立共同記憶

解決方法其實不複雜，只要讓 Chat 和 agent 讀寫同一份執行紀錄就好。這時候 Obsidian 就派上用場了。Obsidian 是一套以 Markdown 檔案為基礎的筆記軟體，所有筆記都存在本機的資料夾（vault）裡。透過 MCP（Model Context Protocol）把 AI 和 Obsidian 連起來之後，流程就變成：Chat 把任務寫進筆記，agent 執行完把結果寫回去，Chat 再讀取結果來驗證。理論上，不同的對話、甚至不同家的 AI，都能讀到同一份紀錄。

等於讓 AI 有了共同記憶。不必再把 prompt 和結果搬來搬去，新開的對話也能從紀錄接續，不會從頭失憶。

> 💡 **兩個小提醒**
>
> 1. 共同記憶要好用，紀錄格式最好固定。例如每筆都包含「日期／任務目標／給 agent 的 prompt／執行結果／待驗證事項」，AI 讀起來才不會混亂。
> 2. 如果處理的是敏感資料（例如病人資料），筆記裡只放流程和摘要，不要放原始資料，也要留意筆記同步到雲端的設定。

## 下一步：檔案管理

有了共同記憶很好，但還有一個很重要的問題要處理，就是檔案管理。原始資料、中間產出的過程檔、程式碼、最後的結果檔，如果沒有好好整理，用 AI 的體驗還是會很卡：AI 找不到檔案、改錯版本、覆蓋掉舊結果，都是很常見的狀況。這裡要認識兩個東西：本機的專案資料夾，以及 GitHub 的版本控制。這部分我們下次再說！
