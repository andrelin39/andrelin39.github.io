## 為什麼想留下這份紀錄

學術網站終於完整上線了。從決定動手到首頁定稿,前後大約三週。回頭看,這不只是「建好一個網站」,更像是一次對自身工作流的重新校準——關於如何與 AI 工具協作、如何把研究者的數位身份系統化、如何在「想做」與「做到」之間建立可持續的路徑。

值得記錄一筆。

## 起點:三次失敗的嘗試

這不是第一次試圖建站。第一次用 Hugo + Academic 主題,卡在「Claude 叫我改某個檔案,我找不到那個檔案」的死循環裡。第二次用 WordPress,陷入主題更新就壞、外掛互相衝突的折騰中。兩次都無聲地放棄。

第三次決定改變策略——**先想清楚,再動手**。

## 「先想、後做」的協作節奏

這次起手式是在 Claude 對話介面裡完整規劃,而非直接執行。確定要用 al-folio 主題(Jekyll 框架,學術圈主流選擇)、釐清網站需要哪些區塊、討論中英雙語架構、思考日常更新的工作流要簡化到什麼程度。等方向都清晰了,才把任務交給 Claude Code 執行。

這個「先構思、後執行」的節奏,讓整個建站過程順暢得超乎預期。

## Claude Code 帶來的根本性差異

Claude Code 是運行於終端機的命令列工具,它與對話式 AI 最本質的差異在於:**它不需要我擔任中介者**。

它能直接讀檔、修改、執行指令、處理錯誤,並在過程中自主分析根因。當我提出「為網站加入中英語言切換」這種需求,它會自動辨識涉及的所有檔案——CSS、JavaScript、Liquid 模板、YAML 資料檔、navbar 元件——並一次性完成所有修改。十分鐘搞定原本需要半天的工作量。

過程中當然遭遇阻礙:Windows 中文編碼導致 Jekyll 崩潰、專案縮圖全部 404、navbar 被擠到變形。但每個問題的處理流程都是相同的——描述現象、等它分析、確認修正——從未需要我親自翻閱技術文件。

## 從建構到設計系統化

完成基礎建置後,我開始追求視覺一致性。教學頁、演講頁、專案頁逐一打磨,讓三大主要展示頁採用相同的設計語言:左側深紫色裝飾條的類別標題、淡紫色外框的按鈕、淺底深字的狀態標籤、數據摘要區塊的大數字呈現。

最後修首頁時,連照片與標題的頂部對齊、中英姓名的並列方式、section 之間的留白節奏都仔細調過。**這些細節讀者不會明確指出,但會無意識地感受到「這個網站看起來很穩」**。

這就是好設計的特性——做對了沒人讚美,做錯了人人皺眉。

## 寫進 CLAUDE.md 的長期記憶

過程中學到最重要的工具觀念是 `CLAUDE.md` 這個檔案。Claude Code 每次啟動都會自動讀取它,等於是「**寫給 AI 看的長期記憶**」。我把每個重要決策都記進去:選擇 Markdown 工作流而非 CMS、教學資料放雲端硬碟而非 GitHub、視覺設計規範、命名慣例、新增內容的 SOP。

這個檔案讓我不必每次重新解釋專案脈絡。下次開啟 Claude Code,它就「知道」這個網站的所有約定。

## 角色邊界的清晰劃分

回頭看三次嘗試的成敗,核心差異在於**人與工具的角色邊界**:

- WordPress 失敗在「**系統太複雜我兜不住**」
- 對話式 AI 失敗在「**我要自己搬磚**」
- Claude Code 成功在「**我負責決策,它負責執行**」

對一個不以寫程式為業的研究者而言,這種協作模式格外珍貴。我終於能把時間花在「**這個網站要呈現什麼**」,而非「**這行語法哪裡寫錯**」。

## 接下來的方向

網站工程已告一段落,身份從「**建構者**」轉換為「**內容累積者**」。每場新演講、每篇新論文、每門新課、每個想法,都能用一句話交給 Claude Code 處理。維護成本降到最低,**累積複利從此開始**。

這個網站不會只是個展示頁——它會是接下來十年學術生涯的數位主場。

## 一個小小的體悟

這次經驗讓我重新理解「AI 工具」的本質。它不是「**能幫我做事的助手**」,而是「**能執行我想法的代理**」。差別在於前者需要我盯著看,後者需要我把方向想清楚。

把方向想清楚,反而才是 AI 時代最重要的能力。
